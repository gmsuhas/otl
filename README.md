# otl

A plain-text event log, turned into one trace.

Nothing to install beyond Python 3.9. No SDK, no collector, no backend. The
point is to see the conversion itself: a start and a stop become a span, a
span opened inside another becomes its child, and the same tree can be written
as the JSON a collector already accepts.

## Where it comes from

[beam-telemetry/telemetry](https://github.com/beam-telemetry/telemetry) is a
small dispatch library. A library calls `telemetry:execute/3` or
`telemetry:span/3`, and anything that attached a handler hears about it. It is
not OpenTelemetry. The project says so, and points at
[opentelemetry-erlang](https://github.com/open-telemetry/opentelemetry-erlang)
and `opentelemetry_telemetry` for the real bridge.

That bridge, and the usual Python getting-started guides, assume you already
want the SDK. Two smaller projects sit closer to the wire:
[posit-dev/picotel](https://github.com/posit-dev/picotel) is a single-file
OTLP client for spans and logs, and
[dimaqq/otlp-json](https://github.com/dimaqq/otlp-json) serialises spans that
the official SDK already built. Neither one starts from a line of text.

otl is the missing picture in front of those. It borrows the shape of a
telemetry span (a name, a start, a stop or an exception, measurements as
attributes) and emits one
[OTLP](https://opentelemetry.io/docs/specs/otlp/#json-protobuf-encoding) trace.
It does not pretend to be the bridge, and it does not speak protobuf.

[ramp](https://github.com/gmsuhas/ramp) writes the line that comes before
this one: a flag decision as a `feature_flag` event on the open span, in
the names the OpenTelemetry registry already records. otl does not decide
the variant. It places the event.

## Try it

```sh
python3 -m otl trace examples/request.log
python3 -m otl otlp  examples/request.log demo 2026-11-08
python3 -m otl page  "One request" examples/request.txt > page.html
```

A line is a clock, a name, a phase, and `key=value` attributes:

```text
12:01:02.100 web request start method=GET path=/
12:01:02.110 db query start table=users
12:01:02.140 db query event rows=1
12:01:02.160 db query stop
12:01:02.190 web request stop status=200
```

`start` opens a span. `stop` closes the most recently opened span of that
name and marks it ok. `fail` closes it and marks it as an error, using the
`error` attribute as the message. `event`, or a line with no phase, is a point
in time on the open span. A start that never closes is kept, with no end time,
rather than dropped or given a made-up duration.

`trace` prints the tree. `otlp` prints one `ExportTraceServiceRequest`: hex
trace and span ids, integer span kind and status, attributes in the `key` /
`value` form, and timestamps as decimal strings of nanoseconds. The service
name defaults to `otl`. The clock in the file is a time of day, so the
export adds it to midnight UTC of the date you pass. Without a date, that
day is today in UTC. A collector accepts the body at
`http://localhost:4318/v1/traces` with `Content-Type: application/json`.
otl does not post it for you.

## The problems it lines up with

Three production failures show up before anyone argues about which backend to
buy. otl keeps each one small enough to point at.

**A span that never ends.** An exception path, a timeout, or a context that
hops a queue and comes back without its parent leaves a span open. The SDK
holds it, memory grows, and the trace in the UI stops short of the operation
that failed. `examples/checkout.log` is that case: `notify` starts, nothing
stops it, and the text view says `unclosed` instead of inventing a duration.
The write-up people hit in production is
[forgetting to close spans](https://oneuptime.com/blog/post/2026-02-06-fix-forgetting-to-close-spans/view).

**A trace that cannot be read back from the logs.** During an incident the
spans are missing and what you have is a timestamped log. Correlating those
lines by hand is the work distributed tracing was supposed to remove, which is
why write-ups of missing spans keep landing on instrumentation gaps and
context lost at a boundary
([why spans go missing](https://ones.com/blog/why-are-opentelemetry-traces-missing-spans-from-some-services/),
[where to start](https://chroniclesofasre.substack.com/p/distributed-tracing-in-a-microservices)).
`otl trace` does the mechanical part of that reading: pair a start with its
stop, and put a span inside the one that was open around it.

**OTLP JSON that a collector rejects.** The JSON mapping is not ordinary
protobuf JSON. `traceId` and `spanId` are hex, not base64, and an enum such as
span kind or status is an integer, not a name. Shipping the wrong one is a
known SDK bug, not a style argument
([opentelemetry-php #1059](https://github.com/open-telemetry/opentelemetry-php/issues/1059),
[opentelemetry-go #1924](https://github.com/open-telemetry/opentelemetry-go/issues/1924)).
`otl otlp` writes that form, and it places the time of day on the UTC date
you give it, so the timestamps are unix time rather than an offset from
midnight.

## What it deliberately does not do

Metrics, the OpenTelemetry log signal, sampling, retries, gzip, and protobuf
are out. Span kind is always internal. The text view still prints a time of
day, and the export needs a date to turn that into unix time. Two spans with
the same name close from the inside out, and a stop with no start is recorded
rather than rejected. All of that is small enough to read straight through.
